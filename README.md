# LocketVideo17 AVFoundation helper

Authorized Locket 2.71.2 integration, arm64, iOS 15+. Only generated helper source belongs in this public repository: never an IPA, app executable, credentials, media, or device logs.

## Scope

- Main agent's Mach-O patches must implement 17-minute capture and remove local library selection limits. This dylib does not change capture, UI, purchase/entitlements, network or postMoment.
- In the `Locket` main executable only, swizzles owned implementations of AVAssetExportSession and currently loaded subclasses: setTimeRange:, setFileLengthLimit:, exportAsynchronouslyWithCompletionHandler:, status, progress, error, cancelExport. No init-family hooking or fishhook dependency.
- External finite video exports get the FULL original asset duration and fileLengthLimit=0 (not the app's 6 MB). Non-video, protected, indefinite/invalid-duration sessions use the original path. Internal-session marker and thread-local original-call guard prevent recursion. Encoding uses no internal export sessions.
- Compatible local MP4/MOV/M4V sources are copied byte-for-byte whenever the container and extension match and no app audioMix/videoComposition needs rendering — **regardless of file size**. A 17-minute ~130 MB recording therefore passes through untouched, preserving quality. Otherwise AVAssetReader + AVAssetWriter render the full duration while targeting quality: source `estimatedDataRate` (resolution table fallback ≈6 Mbps at 1080p, 3 Mbps at 720p), clamped to 500 kbps–12 Mbps; 128 kbps AAC with the source channel count capped at 2; source resolution and frame rate (capped at 60 fps) are retained. Retries happen only on genuine encoder failure or an invalid full-duration result — there is no attempt ladder that shrinks bytes. HEVC failure falls back to H.264. No duration truncation, fileLengthLimit encoding, custom upload, or server-call spoofing.
- **There is no client-side megabyte cap.** Size is not used to reject an export. All size measurements use fresh POSIX stat on regular file URLs, never cached NSURL resource values. Validation checks only duration (0.30 s tolerance for AAC/frame rounding), video presence, and retained audio. A too-short/invalid result fails explicitly; an arbitrarily large valid result is accepted.
- The app itself uploads the resulting file to `gs://locket-video` with the user's token and then calls `postMomentV2`. This helper adds nothing there: no networking, no upload code, no postMoment calls. Server-side acceptance of files above roughly 10 MB is unverified; a `403` at finalize is a Firebase Storage rule decision, not a client bug, and cannot be fixed by a dylib.
- Atomically retained per-session associated state exposes truthful Waiting/Exporting/Completed/Failed/Cancelled, active-pass progress, and NSError. Retries can reset progress. One export invocation's supplied completion is delivered once on a background queue; repeated starts while active join the current job (each supplied callback gets one delivery). A helper session is ONE OPERATION: once its job exists, it is never replaced. Repeated starts after completion/failure/cancellation only asynchronously deliver the new invocation's completion with the same stable terminal status/progress/error; they do not re-encode. A genuinely new export requires a fresh AVAssetExportSession object. Existing output files are NOT overwritten. Async job retains session until terminal state and releases the association cycle; terminal duplicate callbacks also retain the session through callback return. cancelExport is cooperative; cancellation cannot interrupt a blocking AVFoundation read immediately.
- Minimal rotating diagnostics at Documents/locket-video17.log: phases, duration, dimensions, bitrate, byte size, chunk raise, numeric error codes only; no paths, media metadata, identifiers or credentials.
- If the app embeds GTMSessionUploadFetcher, hooks `beginFetchWithCompletionHandler:` there too (gentle no-op if the class is missing). Before the original call, if the receiver's `chunkSize` is between 1 byte and 32 MiB, it is raised once to 32 MiB via KVC `chunkSize` — fewer upload round-trips for huge files. One log line records old→new plus file length. Chunking is client-side only: it does not change Firebase Storage rules, so a finalize `403` remains a server rule.

## Build

Run `.github/workflows/build.yml` via workflow_dispatch on macos-latest. It uses the Xcode iPhoneOS SDK, clang -arch arm64 -fobjc-arc -fblocks -dynamiclib, minimum iOS 15, frameworks Foundation, AVFoundation, CoreMedia, CoreVideo, VideoToolbox, CoreGraphics and AudioToolbox; install name `@rpath/LocketVideo17.dylib`; `codesign --sign -` and verification. Artifact includes dylib, compiler output, dependencies, size and SHA256. Re-sign the entire app normally when packaging for sideloading. Do not modify signed dylib bytes after signing.

## Integration / device checks (NOT performed by CI)

Place LocketVideo17.dylib in Locket.app/Frameworks and load it as `@rpath/LocketVideo17.dylib` with the executable's Frameworks rpath (packaging is outside this helper). Avoid another dylib hooking the same methods after this helper. Preserve the exact executable name `Locket`.

Test a tiny compatible file (byte-identical copy), a large compatible file (byte-identical copy at any size), portrait/landscape + rotated video with audio, 1020-second capture, long library video, multiple exports, duplicate start, cancel mid-copy/encode/finish, existing destination, low disk, and failure paths. Confirm terminal status/error match callbacks, full duration and audio, then test app upload separately. CI only compiles/signs; it does NOT test device playback, app upload or server acceptance.

## Limitations

**No client-side MB cap is imposed by this helper.** Files are not rejected for being large, and a compatible local video is copied without any size-based quality reduction. Actual delivery is still performed by the app uploading to `gs://locket-video` with the user's token, followed by its `postMomentV2` call; nothing is added by this helper. Server acceptance above roughly 10 MB is unverified — historically a finalize `403` indicates a Firebase Storage rule, which this helper cannot change.

Quality is preserved on the copy path; the render-only path targets source-like bitrate/resolution rather than a fixed output size. App-provided video compositions retain their render size/instructions; custom compositor, HDR/Dolby Vision, uncommon codecs, irregular timestamps, iCloud assets, multi-track compositions and later-loaded private AVFoundation subclasses need real-device verification. Metadata/original color/HDR are not guaranteed in a re-encode. Modern async Swift export APIs are not hooked; this helper targets the legacy completion-handler export used by this app. KVO notifications are not synthesized (polling getters and completion handlers are supported). Enabling this source in any executable other than `Locket` is intentionally a no-op.
